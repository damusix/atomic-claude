# Conventions


- Atomic style applies to Claude's TUI replies, not to source files, comments, or documentation. Source files follow the codebase's own conventions.
- `CLAUDE.md` in any project should hold only meaningful context for that codebase — not general advice, not duplicated tool lists. Keep it lean.
- `AGENTS.md` is the authored steering source; at repository and realm scope the `[steering] claude` mode decides what Claude reads: `loader` (default) puts a thin `CLAUDE.md` beside it, `agents-md` writes `AGENTS.md` alone, and `claude-md` writes the guidance into `CLAUDE.md` instead. The global contract lives at `context/AGENTS.md` and each harness adapter renders it into that harness's global file: Claude's global file is the `CLAUDE.md` at its config root (so there is no user-level `AGENTS.md` for Claude), while OMP's profile-root global steering *is* `AGENTS.md` (`omp.SteeringPath` → `<profile root>/AGENTS.md`). An install rewrites only the Atomic-owned block in a global file; user prose outside it survives byte for byte, and repository/realm files keep their unowned content.
- A bare `atomic install` installs into every installed harness and prints what it detected; `--harness <claude|omp|codex>` narrows it, and `atomic harness enroll` enrolls one explicitly. Discovery never enrolls, and `atomic update` reconverges only targets already enrolled, plus a one-time adoption of a legacy Claude install ([what stops it](../guides/install.md#updating)). The per-target ledger is `~/.atomic/install/ledger.json`; `atomic harness status` reports it.
- No AI bylines in commit messages or PR descriptions.
- The scratchpad (`.atomic/.scratchpad/<slug>/`) is LLM working memory — ephemeral, gitignored, not for human consumption. Durable decisions go in `docs/`. It is a slug-keyed bundle, not a dated one: `atomic scratchpad new <slug> --purpose <plan|implement|fix|diagnose|review>` creates or extends it, seeding only what that purpose still needs, so a task worked across several phases accumulates in one directory instead of a new one per phase per date. `atomic scratchpad path <slug>` prints its location, `list [--archived]` enumerates bundles, and `archive <slug>` retires one.
- Session reports and archived bundles live outside the repository, under `~/.atomic/<project-key>/` — one home per clone, shared by every worktree of it. `atomic where --json` resolves the current branch's report path, the reports root, and the archive root for this project; nothing should construct those paths by hand. Run `atomic migrate --show-log` for the history of how this and other state layouts changed.
- `.atomic/` paths throughout these docs describe the default state root. A custom root (`ATOMIC_STATE_DIR`, a selection from `atomic state adopt`, or `state.dir`) replaces `.atomic` in every one of them; the harness-neutral ladder is in [concepts](/reference/concepts#state-root-resolution-order), and `atomic where --json` prints the resolved `state_root`. `atomic state migrate` moves Atomic's state out of legacy `.claude` (into `.atomic` by default), and `atomic repo init` and `atomic update` run it once on their own.
- Tests verify intent, not behavior. A test that still passes when the business logic changes is wrong.
- `tmp/` is for throwaway experiments and ad-hoc verification scripts. Not a scratch directory for checked-in work.
- When `/subagent-implementation` is about to start significant work, it prompts whether to use an isolated worktree. Already inside a linked worktree? It skips the prompt. New worktrees go in `.claude/worktrees/` under Claude Code and in `.atomic/worktrees/` under OMP, Codex, or an unknown harness; the `worktrees` field of `atomic where --json` prints the resolved directory. `atomic workflow set worktrees <path|auto|off>` overrides the placement or turns worktrees off ([workflow preferences](/reference/concepts#workflow-preferences)).
