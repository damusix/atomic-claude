# Plans, specs, and designs

Write a contract a human can approve and an agent can implement. Use the shortest form that preserves scope, behavior, constraints, evidence, and decisions. Separate what is known from assumptions; cite source paths or other evidence for factual claims. Use a diagram when it clarifies the logic, not as a substitute for the contract. Read `mermaid.md` before writing a Mermaid block.

For a design, follow `atomic template design-doc`. Show the end result with brief consumer examples in the project's language or the interface's native format. Use diagrams and tables for logic and data shapes; use language-neutral pseudocode only when needed to make the logic clear. Leave production code to implementation.

Use `atomic template spec` for the disposable scratchpad contract. Separate end-to-end proof from checkpoint checks. Link to flows in the durable design; describe only flows absent there. Follow `rules/specs/spec-currency.md` when amending an existing tracked spec.

Preserve the format of existing frontmatter, code fences, commands, paths, identifiers, error strings, and diagram labels. Do not rewrite unrelated sections for voice as a side effect of an amendment.
