# Repo wiki output formats


## Router


Start `docs/wiki/index.md` with `type: Index` and a one-line `description` in YAML frontmatter, followed by `<wiki-type>repo</wiki-type>`, `<scan-sha>SHA</scan-sha>`, and `<wiki-schema>1</wiki-schema>` on separate lines. `SHA` is the Git blob hash of the accepted scan candidate (`git hash-object <candidate>`).

Use `# Project signals` and these sections in order: `What this repo is` (purpose and primary flow), `Domains`, `Framework & runtime`, `Build / test / lint` (Purpose, Command, Source), and `DevOps & CI`. Keep the router about 200 lines or less. Keep the complete domain map and move details into domain pages. State current facts, not commit history. Do not count repo things; see `atomic-writing/references/documentation.md`, rule 17.

| Domain | Start here | What it does | Detail |
|---|---|---|---|
| auth | `src/auth/` | Session validation | `docs/wiki/auth.md` |

Keep these four columns and one row per domain. Doctor reads the last column. Use one entry path per domain. Write repo-root-relative paths in backticks in the router and domain pages. Do not use `@` references inside them. `atomic signals linkify` makes relative links.

## Domain page


Use `type: Domain`, a one-line `description`, and two or three tags from the existing wiki vocabulary. Use one file per functional concern with these sections in order:

| Section | Content |
|---|---|
| What it does | Purpose before mechanism; explain naming mismatches. |
| How it works | Source-backed behavior and captioned diagrams where they clarify it. Give each diagram after the first its own subheading. |
| Where it lives | One path and responsibility table. |
| Constraints | Invariants and what breaks when they are violated. |
| Coupling | Counterpart domains, callers, and contracts that change together. Link to the owner instead of repeating facts. |

Redraw current architecture diagrams from the assigned designs against source. Leave before-and-after and rejected designs in the design docs. Resolve every node to source and cite the design and source paths with `%% source:`. Report diagrams with stale nodes separately rather than copying them. Follow `atomic-writing` for diagrams and counts. Return judgments under `## Concerns (do not include in domain file)`, with location, observation, and severity. They do not belong in the page.

## Pointer card


Use `<state-root>/rules/wiki/<domain>.md` (`state_root` from `atomic where --json`). Derive `paths:` from the domain's disjoint source partition; directory entries become `dir/**`. For overlapping ownership prefer the longest matching Start here directory, then behavioral ownership, then the narrowest source scope. Report unresolved ownership rather than guessing.

```markdown
---
# generated by /refresh-wiki — do not hand-edit; regenerated every refresh
paths:
  - "src/auth/**"
---

Domain: auth. Session validation

Map:
  - docs/wiki/auth.md

Consult the map before changing behavior here. Behavior changes stale the pages above. Renames or removals stale mentions beyond them: grep the old name across docs/ before shipping.
```

Use the router's description verbatim. After `Map`, add nonempty categories in order: `Contracts` (`docs/spec/`), `References`, `Guides`, `Research`, `Designs`, `Related` (other linked docs). Use linked docs from the domain and applicable designs. Deduplicate and sort within categories. Use one nested line per path, at most twelve links including the map, and omit the weakest links first. Other than the header, description, categories, and fixed closing line, add no prose.

## Wire the router


Read `[steering] claude` from `<state-root>/atomic.toml`, then `~/.atomic/config.toml`; the default is `loader`. Read shared wiki steering if present, otherwise `docs/wiki/CLAUDE.md`. Wire root instructions using the configured mode:

| Mode | Steering source | Claude routing |
|---|---|---|
| `loader` | `AGENTS.md` | Ensure the adjacent `CLAUDE.md` imports `@AGENTS.md` without overwriting existing instructions. |
| `agents-md` | `AGENTS.md` | Do not create `CLAUDE.md`. |
| `claude-md` | `CLAUDE.md` | Do not create `AGENTS.md`. |

Prefer an existing project-local override for the root ref. Check existing routing first; a ref in an inactive file is not wired. Insert only the router ref before behavioral instructions. Create missing root instructions only with the caller's approval; otherwise report that routing was skipped. Do not wire the scan or wiki steering file by reference.

```markdown
<atomic-signals>

## Project signals (auto-loaded)

@docs/wiki/index.md

</atomic-signals>
```

When loader mode needs a new `CLAUDE.md`, use the same block as the CLI. If that file already holds user instructions, preserve them and add `@AGENTS.md` only if the file does not already load it.

```markdown
<atomic>

@AGENTS.md

</atomic>
```

### Loader-mode ref wiring

When wiring an existing steering file in `loader` mode, run this snippet. It preserves already-loaded refs and skips symlink loaders.

```bash
ref='@docs/wiki/index.md'
if ! grep -qsF "$ref" claude.local.md CLAUDE.local.md CLAUDE.md claude.md; then
  if ! grep -qsF "$ref" AGENTS.md; then
    target=
    if test -f AGENTS.md; then target=AGENTS.md
    elif test -f CLAUDE.md; then target=CLAUDE.md
    elif test -f claude.md; then target=claude.md
    fi
    test -n "$target" && cat >> "$target" << 'EOF'

<atomic-signals>

## Project signals (auto-loaded)


@docs/wiki/index.md

</atomic-signals>
EOF
  fi
  if grep -qsF "$ref" AGENTS.md; then
    for loader in CLAUDE.md claude.md; do
      if test -f "$loader" && ! test -L "$loader" && ! grep -qF '@AGENTS.md' "$loader"; then
        printf '\n@AGENTS.md\n' >> "$loader"
      fi
    done
  fi
fi
```
